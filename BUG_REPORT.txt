CATEGORY 2: CORE FINANCIAL, LOAN MANAGEMENT & ACCOUNTING LOGIC (9 ISSUES)
--------------------------------------------------------------------------------

[BUG-05] [CRITICAL] Overdue Loan Principal Silently Erased During Restructuring
- File: internal/loans/admin_handler.go (AdminRestructureLoanHandler: Lines 229-245)
- Description: The restructuring loop only collects installments where
  inst.Status == models.EmiStatusPending. If an installment is overdue (EmiStatusOverdue),
  it is skipped from pendingIDs and omitted from remainingPrincipal, while advancing
  maxPaidInstallmentNumber. The overdue principal balance is permanently erased from the
  new amortization schedule without being collected or accounted for in the ledger.

[BUG-06] [HIGH] Non-Transactional EMI Amortization Schedule Re-Generation
- File: internal/loans/admin_handler.go (AdminRestructureLoanHandler: Lines 255-263)
- Description: Pending installments are permanently deleted from the database before
  invoking generateEmiInstallments outside of a database transaction. If schedule creation
  fails (due to a math exception, DB error, or process crash), all future installments are
  lost permanently with no rollback.

[BUG-07] [CRITICAL] Defective Accounting Entry for Loan Payment Refunds
- File: internal/accounting/postings.go (PostRefund: Lines 153-166)
- Description: When an EMI is paid, it is credited between AcctLoanPrincipalReceivable
  and AcctInterestReceivable. When PostRefund is triggered, it debits 100% of the refund
  to AcctLoanPrincipalReceivable. This artificially inflates the Principal Receivable
  ledger account by the interest component, distorting the balance sheet.

[BUG-08] [HIGH] Post-Disbursement EMI Schedule Generation Loss Outside Transaction
- File: internal/loans/confirm_disbursement.go (ConfirmDisbursement: Lines 87-104)
- Description: The database transaction commits disb.Status = SUCCESS and
  loan.Status = DISBURSED before invoking generateEmiSchedule. If generateEmiSchedule
  fails, the function merely logs an error and returns nil. Money is marked disbursed to
  the borrower, but no repayment schedule exists in the system.

[BUG-09] [HIGH] Month-End Calendar Overflow in EMI Due Date Calculation
- File: internal/loans/emi_service.go (generateEmiInstallments: Line 73)
- Description: dueDate := baseDate.AddDate(0, i, 0) produces calendar overflow for month-end
  dates. If a loan is disbursed on Jan 31, installment 1 is computed as March 3 (skipping
  February entirely) and installment 2 is March 31, creating two EMIs in March and zero in February.

[BUG-10] [MEDIUM] Binary Status Blindness in Delinquency & DPD Calculation
- File: internal/risk/dpd.go (CalculateDPDForLoan: Lines 53-59)
- Description: The DPD engine assumes installments are either 100% paid (EmiStatusPaid)
  or 0% paid. It never inspects partial payments in models.Payment. If a borrower pays
  90% of an EMI, the entire due amount is treated as outstanding and DPD accumulates on
  the full sum.

[BUG-11] [HIGH] Unbounded Proliferation of Stale Active Risk Provisions
- File: internal/risk/provisioning.go (CalculateProvision: Lines 90-101)
- Description: When daily risk calculation detects no change in exposure, it inserts
  a new provision row with Status = ProvisionStatusActive without deactivating or superseding
  the previous day's row. Over 30 days, 30 active provision rows exist for a single loan,
  multiplying provision totals in aggregate reporting.

[BUG-12] [HIGH] Premature NOC Certificate Generation for Undisbursed / Non-Disbursed Loans
- File: internal/loans/noc.go (CheckAndGenerateNOC: Lines 47-64)
- Description: CheckAndGenerateNOC queries models.EmiInstallment for any status != paid.
  For an undisbursed, cancelled, or rejected loan with 0 installments created, remaining
  evaluates to 0, causing the system to generate an official No Objection Certificate (NOC).

[BUG-13] [HIGH] Write-Off Approval Does Not Update Loan Status or Cancel Future EMI Installments
- File: internal/writeoff/service.go (ApproveWriteOff: Lines 53-105)
- Description: When write-off is approved, only WriteOffRequest status is updated to WRITTEN_OFF
  and accounting entries are posted. The LoanApplication record status remains DISBURSED, and
  associated EmiInstallment rows remain pending/overdue. As a result, automated DPD calculation,
  delinquency classification, collection jobs, and daily interest accrual continue running
  against a loan that has already been written off.

CATEGORY 3: TAX (TDS / GST) & STATUTORY COMPLIANCE ENGINES (3 ISSUES)
--------------------------------------------------------------------------------

[BUG-14] [CRITICAL] Single-Transaction vs. Annual Cumulative TDS Threshold Evasion
- File: internal/tax/calculate.go (CalculateTDS: Lines 62-69)
- Description: Under the Indian Income Tax Act (Sections 194C, 194J, etc.), deduction
  thresholds are annual/financial year cumulative limits. The code only checks
  grossAmountPaise < rule.ThresholdPaise on the current single transaction. Vendors
  submitting multiple invoices below the single threshold completely evade TDS.

[BUG-15] [HIGH] Fractional Timestamp Error in Daily Interest Accrual
- File: internal/accounting/accrual.go (AccrueInterestForLoan: Line 60)
- Description: days := periodEnd.Sub(periodStart).Hours()/24 + 1 calculates elapsed days
  using floating-point hours. For end-of-day timestamps (e.g. 23:59:59) or daylight
  shifts, it computes fractional/extra days, miscalculating interest recognized.

[BUG-16] [CRITICAL] Missing RBI IRACP NPA Interest Derecognition & Suspense Handling
- Files: internal/accounting/accrual.go & internal/risk/job.go
- Description: Under RBI Master Direction - Prudential Norms on Income Recognition,
  Asset Classification and Provisioning (IRACP), when an account turns NPA (>90 DPD),
  unrealized interest must be reversed and further accrual diverted to Interest Suspense.
  The engine continues standard accrual and income recognition.

- Description: ForgotMPINHandler checks Where("mobile = ? AND verified = ?", mobile, true)

- Description: When a user calls /auth/change-mpin, failed attempts on CurrentMPIN
  have no rate limit, counter, or lockout. An attacker with a compromised session can

[BUG-19] [MEDIUM] Ineffective Client Logout (Token Revocation Absent)
- File: internal/auth/logout.go (Logout: Lines 9-13)
- Description: The Logout handler simply returns a static JSON message. It does not
  add the JWT to a blocklist or revoke active sessions. Compromised tokens remain valid

[BUG-20] [MEDIUM] Customer JWT Token Lacks Subject (UUID) Claim
- File: internal/auth/jwt.go (GenerateToken: Lines 35-48)
- Description: Customer tokens contain only mobile in their claims. Every request
  requires an unnecessary database lookup to resolve the UUID, opening race conditions
  if mobile ownership shifts.

[BUG-21] [HIGH] Concurrent Race Condition Bypassing OTP Attempt Threshold
- File: internal/otp/service.go (VerifyOTP: Lines 101-132)
- Description: VerifyOTP performs a non-locking select, checks Attempts < 5, and
  increments via an application-level update. Concurrent requests bypass the 5-attempt limit.

[BUG-22] [CRITICAL] Reversible MPIN Stored Locally for Biometric Login
